## 2. Actual integrated production trace (all paths pinned to `175ace9`)

### A. USB speaker path / PCM and gain

`src/tinyusb/uac.c:939–971`: `tud_audio_rx_done_pre_read_cb()` reads interleaved 16-bit stereo from the speaker OUT endpoint, optionally logs the **pre-gain** `U` USB tap, calls `set_usb_streaming(true)`, then `audio_slot_push_samples(src, spk_data_size/4)`.

`src/btstack/btstack_avdtp_source.c:896–973`: `audio_slot_push_samples()` copies interleaved L/R samples into the audio-slot pool with the selected Q15 software gain; it does not apply a mic-state-specific channel map. `audio_slot_pop()` (`:994–1048`) can prime silence, mix a separate relay stream, and apply stereo fade boundaries; this is **after the USB tap** and **before FDK**. The actual diagnostic at `:1348–1375`, `src_eld_pcm_tap_note()`, instead measures the stereo buffer *after* gain, mixing and any optional 44.1-to-48-kHz resampling, immediately before FDK. Thus the November 7 phase-matched left peaks supersede the earlier unresolved host/gain-boundary question, while remaining silent on the codec's output.

### B. Encoder lifetime / AAC content

`src/btstack/eld_profile.c:3–27`: `eld_profile_select()` uses rate, game, level, input rate, relay and VBR/SBR settings **without reading microphone capture state**. The actual mic-capable `USBPODS_MIC_DECODE` build forces CBR/SBR-off. The physical standard profile was 256 kbps; 192-kbps and game-mode profiles are separately negotiated and were tested. A 320-kbps setting was skipped because the peer accepted a 256-kbps ceiling.

`src/btstack/eld_encoder.c:4–24`: `eld_encoder_open()` closes the old handle, configures FDK AAC-ELD AOT 39, **48 kHz, MODE_2 stereo, 480-sample frames, raw access units**, and validates `frameLength==480` and `inputChannels==2`. This is an encoder *configuration contract*, not measured output channel content.

`src/btstack/btstack_avdtp_source.c:1379–1525`: `codec_fdk_fill()` removes a stereo audio slot, points `AACENC_InArgs` at its interleaved PCM, samples the `[eld-pcm]` peaks immediately before `aacEncEncode()`, checks the encoder return status, then appends its output as Apple 4-byte AU headers: 12-bit frame sequence and 12-bit AU size. In the mic build, foreground work normally encodes one AU per pass (`:1337–1344`, `:1422–1454`); packet staging bounds the completed packet to **two AUs** (`:1528–1541`). This path contains no explicit left/right mutation on mic close. Nevertheless FDK's *actual compressed output* and any post-encode corruption have not been examined across the physical fault.

`src/btstack/btstack_avdtp_source.c:508–667`: `a2dp_source_eld_send()` validates **AU header structure and intra-packet sequence**, records transmit attempts and nonzero media-submit return codes, calls `a2dp_source_stream_send_media_payload_rtp()` once with the same stereo AAC payload, then advances its millisecond wall-clock RTP reference. The marker is zero. The header walker does **not** decode the AAC content, establish the left-channel waveform, verify peer receipt, or necessarily detect a lost entire packet. Also `src_tx_pkts++` occurs **before** the media API return, so a rising packet count is **not** a count of acknowledged on-air deliveries. The reference fork uses a different sample-count-based RTP timestamp; changing this policy is **not** supported by the channel-loss evidence.

### C. USB mic close / capture generation / AACP

`src/tinyusb/uac.c:613–694`: `tud_audio_set_itf_close_EP_cb()` on **mic alt 0** calls `usb_capture_close()` and returns without calling the speaker alt-0 flush path. A redundant mic alt-1 close event does not drop capture. Speaker alt-0 separately calls `audio_slot_request_flush()`, `set_usb_streaming(false)` and tap reset; this is not what the direct mic-close code requests. `src/tinyusb/usb_capture_lifecycle.c:5–28` publishes capture only if mounted, not suspended and mic alt-1. `src/btstack/aacp_mic_audio.c:10–31` increments the capture generation when that Boolean actually changes.

`src/btstack/aacp_mic.c:101–111, 157–273`: `aacp_mic_poll()` and the CAN_SEND_NOW handler recompute USB capture intent; `aacp_mic_next()` selects STOP when capture is unwanted and the local AACP session previously marked START sent. The handler sends the existing **12-byte AACP STOP** over the control L2CAP channel. On a successful *local* `l2cap_send()` return it updates `session.started`, resets the microphone watchdog and increments the AU/PCM discontinuity generation; this **does not acknowledge a peer state transition**. There is **no direct AVDTP STOP, playback rebuild, ACL reconnect, or mic-triggered jitter write** on the ordinary START/STOP path. The watchdog's bounded microphone-only STOP/START retry is separate.

`src/btstack/aacp_mic_protocol.c:5–25` contains handshake/feature/notifications/START/STOP arrays with lengths **16/14/10/19/12**, byte-identical according to the pinned `references/research-history.json` comparison against the licensed han-um snapshot `d18d083bc52de3143d8d922c4abaae865cc0dc28`. Neither implementation documents a per-ear routing selector in these sequences; no undocumented wire byte should be invented.

### D. AACP control and jitter; independent playback recovery

`src/btstack/aacp_mic.c:184–198` queues one playback-jitter policy reapply when a **new AACP channel opens**, not on ordinary mic START/STOP. `aacp_control.c` owns the validated control `0x0b` setter, while `src/btstack/btstack_avdtp_source.c:1786–1807` defers an applicable jitter write until stable playback (typically 500 ms after START). Explicit profile/game changes also select jitter. Other independent splice/recovery code can issue jitter or an ELD recovery (`btstack_avdtp_source.c:2263–2282, 2424–2455`); whether any such event coincided with the observed mute is **not** established by the sanitized peak windows. The earlier lifecycle-specific `0x0b=150` write was removed before the present physical candidate. Do not reintroduce it or conflate a queued policy write with a successful peer application.

`src/btstack/btstack_avdtp_source.c:3874–3877`: manual `K` calls `a2dp_source_recover_eld_stream()`; `:1971–1994` requests a **forced** managed change. `:1763–1773, 2160–2196, 3017–3051` subsequently SUSPENDs the playback media, **reopens/reconfigures the FDK encoder**, resets the AU sequence and RTP timestamp, issues AVDTP START and resumes the pump only after START acceptance; pending jitter is applied independently after stabilization. Consequently the successful `K` intervention **resets both the sender's codec/transport state and the receiver's playback session**. It is not an experiment isolating the peer.

## 3. Ranked hypotheses and explicit falsifiers

Ranking is **investigation priority, not a posterior probability**. The first two remain distinguishable only after codec-output evidence. None is a confirmed cause.

| Rank | Hypothesis | Support | Contradictions / limits | Concrete falsifier |
| --- | --- | --- | --- | --- |
| **1** | **AACP STOP changes the AirPods' receiver/left-ear decode or TWS render state**, even though the source continues one valid stereo stream | Audible left tracks AACP START/STOP-intended capture changes with a continuously open speaker endpoint; post-gain PCM remains left-only; normal capture close does not request sender ELD rebuild. A `K` stream renegotiation with capture closed restores sound. Upstream one-ear symptom is context, not proof. | Peer internals and received AAC are unknown; a sender payload problem could also be reset by `K`. Working reference sends the same STOP bytes without a reported requirement to refresh. | Independently decode the **actual fault-phase emitted AUs**, and find that the left tone is **absent or badly corrupted only in the closed phase**. That falsifies an exclusively peer-side diagnosis. If AUs remain correct, require transport/delivery evidence before concluding peer fault. |
| **2** | **FDK encoder output or per-AU packing loses/changes the left channel after mic close despite valid input** (state/timing corruption, damaged access unit, wrong encoded channel structure) | Current `[eld-pcm]` is immediately upstream of FDK; header validation never decodes AAC. `K` reopens the encoder and could repair encoder state. No real fault-phase output has been decoded. | Ordinary AACP STOP never explicitly reconfigures the encoder; **reopening mic** restores sound without a codec rebuild, which argues against a permanently latched FDK fault. Real-FDK synthetic stereo tests already pass in CI, so a simple unconditional channel swap is less credible. | Capture complete AU bytes immediately after FDK / before RTP in stable open, closed, reopened states; with matching ASC and packet boundaries, decode them offline and demonstrate **comparable left-only channel energy/frequency** in all three states. |
| **3** | **RTP submission, AU framing/sequence, packet loss or post-encode staging changes at close** and triggers sink-side one-channel behavior | Only structural AU header walk and local send-return diagnostics exist; `src_tx_pkts` counts attempts; K resets sequence/timestamps and starts a fresh stream. | Both ears share a stereo media stream, so ordinary packet loss would tend to affect more than the left ear; steady measured intervals have positive TX progress. No phase-aligned malformed/send-failure evidence was provided. | For the fault window show valid full AU bounds and continuous packet/AU seq/timestamps, correct decoded payload **at the actual RTP handoff**, successful local submission, and (if possible) link/radio delivery. | **4** | **Independent jitter write, auto-kick, ELD state transition or speaker endpoint churn** happens to coincide with mic close | AACP channel-open jitter setup, explicit profile jitter and independent stall/splice recovery paths exist; earlier `0x0b=150` mic-lifecycle side effect was physically observed in historical evidence. | That extra lifecycle write is removed; direct mic alt-0 callback does not flush speaker or change ELD, the final controlled playback endpoint stayed open, and no matching reset/wire-control event has been established. | A time-correlated trace shows mic STOP but **no** `0x0b` write, AVDTP SUSPEND/START, encoder revision change, speaker alt change or automatic-kick counter delta within the failing interval. |
| **5** | **USB host, gain, relay/mixer or PCM buffering erases the left samples** | An older laptop enhancement produced mixing, and the USB/pool/mixer are separate boundaries, so earlier pre-gain data alone could not dismiss this. | New phase-matched **post-gain/mixer and immediately pre-FDK** L≈316/R≈1 persists when silent. Saved-bond reconnect restores left playback with capture still closed. Earlier PC had no MaxxAudioPro; the final laptop enhancement was disabled. | Continuous matched windows around the complete close event confirm correctly ordered left-only input immediately before all FDK calls, with no transient no-left interval; a fault-phase correct AAC decode further rules out this upstream class. |
| **6** | **Ear-detection, Conversation Awareness, HFP/card profile, gesture or other independent peer control** selects/suppresses left rendering | LibrePods Linux history mentions card-profile switching and capture-time Conversation Awareness; `aacp_control.c` receives ear notifications and supports optional controls. | Firmware contains no automatic mic-close CA policy, no evidence of host HFP profile change, and no validated ear/gesture transition timed to the fault. Linux audio stack is not the Pico. | Time-align validated ear/control notifications, HFP/HCI/AVDTP state and the acoustic event, showing no correlated change; an output AU decoder test can distinguish this from sender corruption. A lack of known notifications does not rule out unknown peer-internal state. |

**Key inference:** Valid left pre-encoder PCM *disfavors* host/gain loss, but it cannot prove valid compressed left output. Conversely, a recovered left ear after `K` cannot prove peer routing because `K` also reinitializes the encoder and the media session. The fact that mic reopen succeeds **without** explicitly rebuilding FDK is evidence *against* persistent sender-encoder corruption, but it does not exclude a transient or scheduling-dependent output defect.

## 4. Minimal discriminating experiment (planned, not implemented or run)

**Priority A — no protocol or routing change:** Preserve the established single-core profile and one continuously open playback endpoint. Correlate existing `[eld-pcm]` open/closed/transition windows with AACP STOP *successful local submission*, mic generation, local AVDTP streaming phase, encoder rebuild revision, active profile/jitter, actual AU count, RTP timestamps, media-submit failures, codec errors and the listener's left/right result. Use a monotonic timestamp for each state edge; the current 500-ms peak summary alone may straddle a short transition. Identify **AACP on-wire intent vs local SDK return vs peer acknowledgment** as distinct states. Explicitly record whether any new AACP jitter control or playback recovery was *actually* sent; do not assume deferred intent was delivered.

**Priority B — most valuable new visibility (future implementation only):** Add a **bounded, opt-in, post-`aacEncEncode` AAC-ELD AU snapshot** at the prepared packet / RTP-handoff boundary, with the exact encoder config/ASC, AU sizes and 12-bit sequences, packet grouping, RTP timestamp/marker, send-return status and capture-generation labels. Use a strictly finite capture budget (e.g. a few hundred milliseconds per stable state, not continuous logging), preallocated storage only if target linker-map/heap/stack headroom permits, no allocation or blocking CDC print in the radio/USB IRQ, and an overflow/skip marker rather than starving real-time audio. The compressed payload is still **private audio**; keep raw AU bytes and any recorded playback locally, never commit/upload them. If safe budget/storage cannot be demonstrated, defer this capture rather than damaging real-time playback. Headers and hashes **alone do not prove left-channel content**.

A private, separately authorized analysis of these emitted AUs must independently decode the **actual phase-matched payload** with the matching AudioSpecificConfig and quantify left/right tone frequency and RMS/energy (not merely checksum, bitrate, header validity or FDK API status). Compare stable open, stable closed and reopened; if a closed-phase AAC decode contains valid left while the ear is silent, the remaining uncertainty moves to radio delivery/peer decoding or rendering. If the decoded left vanishes only on close, local encoder/packet construction becomes primary. A correct local decode cannot itself prove on-air delivery.

**Priority C — CI-only synthetic negative/positive controls:** Extend `tests/test_pcm_packet_path.py` (which already executes production PCM gain, `codec_fdk_fill()`, Apple AU framing, real FDK decoding, gain and channel order) with deterministic left-only and right-only tones across **mocked USB mic alt-1 → alt-0 → alt-1**, while playback remains running and encoder handle is unchanged. Verify FDK input and decoded L/R energy, correct AU headers and seq wrap, payload limits, and absence of unwanted AVDTP recovery or jitter writes. Use intentionally swapped/zeroed decoded-channel negative controls so a test cannot pass solely from a nonzero output size. Keep or extend `tests/test_mic_recovery_integration.py`, `tests/test_aacp_transport.c`, `tests/test_usb_control_boundaries.py`, `tests/test_eld_adapter.py` and the production capture callback tests for stale generations, failed AACP sends, unchanged playback state and explicit `K` recovery. Tests should execute production bodies and deterministic transport mocks, not just grep source strings. Run **all firmware and native FDK/codec tests, including negative controls, exclusively in GitHub Actions**, with exact source SHA, artifact IDs and matrix outcomes recorded.

**Priority D — decision gate, not a default reset:** If real closed-phase AUs decode with intact left audio **and** no correlated jitter, endpoint churn, AVDTP reconfiguration or locally detected media anomalies occur, the best remaining working hypothesis is a peer-side state/transport reaction to AACP STOP. That still requires bounded hardware confirmation (and ideally evidence of reception). If emitted AUs lose left data, investigate sender codec state, buffer ownership and post-FDK packet handling first. Do **not** add an automatic `K`, forced ACL reconnect, undocumented AACP bytes, altered clock/RTP, changed EQ, forced CA control, or permanent capture after host alt-0 as a shortcut. Keep user-invoked `K` fully functional.

## 6. Short physical acceptance after CI and authorization (not performed)

On the **hash-verified single-core** candidate with enhanced audio disabled, maintain **one** speaker endpoint open and a continuous isolated tone. Enable the existing short `U` / `[eld-pcm]` tap and any new bounded output diagnostic only for the necessary windows:

1. Record a stable **left-only** tone with mic alt-1/open; confirm audible left, pre-FDK left-dominant PCM, codec/TX state.
2. Without closing speaker playback, set mic alt-0/closed; confirm capture=0 and STOP local-send status; record left-ear result, at least two stable closed-state windows, output AU content and no accidental AVDTP or speaker-alt transition.
3. Reopen mic alt-1; confirm left audible again and right-channel isolation in a separate short right-only segment (retain the earlier correct-right observation as historical evidence).
4. If left is silent at closed state, use **at most one explicit manual `K`** with mic still closed as a bounded control; retain encoder revision, AVDTP result and decoded-AU comparison before and after. Preserve first-fault data. Saved-bond reconnect is an existing alternative control, not an automatic mitigation and not necessary if this control already distinguishes the result.
5. Stop recording and restore standard 256 kbps/game-off preferences; record source SHA, workflow, artifact hash and actual acoustic result separately. **No additional ten-minute soak**, no unpublished private files or pairing details in GitHub.

**Acceptance:** isolated left and right audible in the correct ears across open, closed and reopened microphone, while capture really stops on alt-0 and playback remains independent. Correct logs, intact PCM, a successful `K`, a valid AU header or a successful build **alone** are not acceptance.
